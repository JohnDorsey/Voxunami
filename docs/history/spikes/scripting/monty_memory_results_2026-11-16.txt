Monty memory limit: measurements behind `max_model_memory` (2026-11-16)
=====================================================================

All measured on the owner's Windows machine (x86-64). "debug" = unoptimized test build, "release" = optimized.
The probe source is `monty_memory_probe/memory_probe.rs` (a scratch example that was built inside the fork's
`crates/monty-runtime/examples/` and removed again; it installs `monty-alloc` as the global allocator).

1. Is the allocator-backed `max_memory` repeatable? (debug, limit 1,000,000 bytes, step at which MemoryError fired)
-------------------------------------------------------------------------------------------------------------
condition                                   small lists   strings      dict of ints
quiet process, 4 runs, 2 processes          55,296 x8     425,995 x8   157,706 x8
another thread allocating 20-170 KB blocks  32,776-41,216 214,341-249,675   90,122
host structure grew 300 KB after arming     36,864        425,995      90,122
(The "strings" script of that probe appended 'k%d' % i. I infer, from the model counting exactly 16 bytes an iteration
on it, that such strings live inside the value and cost no heap object, so that script really measured one list growing
in place. The numbers are repeatable only in a quiet process, which is the point.)

Reading: repeatable only when nothing else in the process allocates; up to 40 percent earlier with a busy thread.
Without monty-alloc installed (an embedding in another program) the limit stops only single oversized requests; a loop
that keeps many small objects ran until the time limit.

   session ran the script, model = MontyRepl::model_bytes() afterwards)

First attempt (dict entry 48, set entry 32, no boxed-payload price): dicts 0.57, instances 0.56, sets 0.75; the prices
were raised to the values above. Measured sizes of boxed payloads: Instance 104, NamedTuple 104, Class 152, Module 152,
ReMatch 160, Partial 64, LruCache 120 bytes (one price of 112 is used for all). A heap entry is 96 bytes, not the 104 I
first guessed; a unit test now compares the price with `size_of::<HeapEntry>()`.

3. What does it cost in time? (release, median of 7 runs, ns per step; committed state `ad80eef5` against the new tree)
-----------------------------------------------------------------------------------------------------------------------
case                                  committed   new, no model limit   new, limit far away   new, 15 MB hugged
plain arithmetic loop (27M steps)        4.20           4.23                 4.24                  4.26
allocating loop, garbage (7M steps)     13.04          12.50                12.54                 12.58
allocating loop, 100k-object live heap  12.95          12.79                13.28                 11.80 (but +44% steps, +33% time)
The first round on the new tree was 7-17 percent slower across the board with the machine busy (another session was
running tests); the second round, quieter, is the one above. Hugging the limit with a large heap costs time because walks
must be frequent there; the price is bounded (at most two slot visits per step) and is charged to the step budget.

5. Disk lesson
--------------
Cargo's `target/debug/incremental` directories held about 34 GB on E:. Deleting them freed the drive; building with
CARGO_INCREMENTAL=0 keeps them from coming back. The release build of `monty-runtime` (it links the type checker) needs
many GB for bitcode and filled the drive; the timing was done with a test in the `monty` crate alone.
