# Painting on a block in the game: options for VirtualAtlas and the game

**A proposal; of its steps, 1 (the picture override), 2 (the CPU surface hit and its mapping, with the oracle), 3 (the bridge) and 4 (VirtualAtlas's side) are built; see "Built so far" at the end.** Written 2026-11-15 on the branch `graphics-world-painting`. The owner asked to plan and explore, not to build. Claims are marked: **[read]** I read it in the code or a document, **[believed]** my reasoning, not run, **[measured]** run, **[not checked]** a question I did not look into.

## The goal, in the owner's terms

Paint on a block's face in the running game, with `plugins/base_blocks/textures/VirtualAtlas.py` (VA) as the painting tool, while the picture used for editing is the game's own rendering, with any pack or shader pack, as the player sees it. Cave must grow as little as possible. The tool is for developers: a player leaves it uninstalled. (The owner first asked that it open no way to cheat and then, 2026-11-15, dropped that; section D.)

## What is true today

- **[read]** The base blocks' pictures are `include_bytes!` in `plugins/base_blocks/src/lib.rs`. They go into the package (raw RGBA, no PNG on the wire) and the client builds one texture array for each picture size (`renderer/src/block_textures.rs`). A face's picture is one word: bit 0 "has a picture", bits 1 and 2 the size class, bits 3 to 10 the layer. That word is already a tile identity.
- **[read]** Texture packs (`block-textures-spec.md`, D9: a client folder that overrides a face's picture, cosmetic, replays unaffected) are specified and **not built**; no code mentions them.
- **[read]** Shader packs change live: `.shader NAME` and `.shadersetting` call `set_shader_pack_with_settings`, which makes the shaders again. Nothing watches files on disk, and there is no `/reload` (`architecture-review.md` A6 says so; no file-watching crate is a dependency).
- **[read]** A client plugin's context has `target()`: a CPU ray hit with the grid, voxel, the voxel before it and the distance. It also has `send_command` and `send_message`, so a client plugin can act for the player.
- **[read]** The renderer can render to an offscreen texture and read it back (`render_to_rgba`, used by `--screenshot`). Features of a shader are compiled in or out (`pictures_on`/`pictures_off`, `relief_*`), so a feature that is off costs a player nothing.
- **[read]** VA is one Python file (5,233 lines) that keeps one PNG for each tile and an `atlas.json`. It has no way to talk to another program.
- **[read]** `architecture-review.md` D.3 already draws the line: a client mod that only changes what this player sees and hears is allowed; resource packs are safe from the start; client code mods come after server mods, in a sandbox with a narrow API. The client regenerates terrain from the seed, so it already knows terrain the player has not seen.

## Four questions, kept apart

The owner's idea (video out, mesh and hovered name out) answers the first two together. They have separate answers, and the best answer to each is different.

### A. How does the painter see the game?

| | What | For | Against |
|---|---|---|---|
| A1 | **The game's own window is the view.** VA is a second window with the tools. In a paint mode the game frees the cursor and sends VA the pointer's tile pixel and the buttons. | No video at all; "exactly as the player sees it" is trivially true; least code. | Two windows. The brush guide has to be drawn by the game (see C). |
| A2 | VA captures the game's window from the screen. | Nothing added to the game for pixels. | The frame and the pointer's answer drift apart (they come by two roads); DPI and a covered window break it. |
| A3 | The owner's: the game writes each frame into shared memory (or a shared GPU texture) and VA shows it. | One window; VA can draw over the 3D view. | A frame is 3.7 MB at 1280 by 720 (about 110 MB/s at 30 per second, **[believed]** fine in shared memory, not measured). A shared GPU texture from Python is a large piece of work **[believed]**. |
| A4 | **VA asks and the game answers**: VA sends a camera, the game renders it and returns the frame with its pick map in one reply (`render_to_rgba` is the seed). | The frame and the answer cannot disagree. VA owns the window. | A request and answer for each frame; the game's window may be hidden or a second renderer. |
| A5 | **One frozen frame.** On a key the game sends VA a snapshot: the frame, the pick map and the table of names. VA paints against the snapshot; the live game shows each stroke at once (C). | No streaming, no sync, no hurry. The first thing to build, **[believed]** and it grows into A3 or A4 if wanted. | Moving the camera means a new snapshot. |

**What a frame through the CPU costs [measured, 2026-11-15, throwaway programs not kept].**

- *GPU to CPU, in the game's process:* reading a 1280 by 720 texture back (a copy to a buffer, mapping it, then copying the bytes out) takes **0.64 to 0.73 ms for the colour frame (3.7 MB)** and **1.13 to 1.22 ms for an 8-byte-a-pixel pick map (7.4 MB)**, on the RTX 3090 and the AMD integrated GPU, each on Vulkan and DX12. Mapping alone is 0.2 to 0.35 ms. Caveat: the texture was never drawn into, so this is the transfer and not waiting for a frame to finish; the frame's own render time is on top of it (which `--benchmark` already reports).
- *Shared memory to pygame, in the Python process* (Python 3.11, pygame 2.6.1, 1280 by 720, the dummy video driver, so the window's own present is not in it): copying the colour frame out of shared memory 0.46 ms; the pick map 0.92 ms; a lookup of one pixel of the pick map is free; a sequence-number check around a copy costs nothing measurable. **Blitting is where a trap is: an RGBA surface costs 8.0 ms because pygame blends the alpha; the same bytes as an `RGBX` surface (alpha ignored) cost 0.27 ms.** So the road from the game through shared memory to the screen is about 2 to 3 ms a frame in all, well inside 16 ms, with no GPU sharing at all.

**Sharing the GPU texture itself, researched 2026-11-15** (by a research agent; marks: [V] verified in source or documents, [R] reported by a forum, issue or README, [I] inferred). I re-checked the wgpu-hal claim in the local source myself.

- **wgpu 30.0.1 can import a shared texture and cannot export one [V, I grepped `wgpu-hal-30.0.1`].** DX12 has `texture_from_raw` (import) and exposes `raw_device()` and `raw_resource()`; there is no `CreateSharedHandle` or `OpenSharedHandle` in the crate, and its textures are never created with the shared heap flag. Vulkan has the feature `VULKAN_EXTERNAL_MEMORY_WIN32` and `texture_from_d3d11_shared_handle`, again import only, with no export call. So a wgpu-made texture cannot be handed to another process; the way round is hand-written unsafe code that creates the shared resource on the raw device, shares its handle, and wraps it with `create_texture_from_hal`, plus fences between processes. The published examples (cef, vtsampler, wgpu-native-texture-interop) all import.
- **Spout is a poor fit [V, R].** It shares DirectX 11 textures (a DX12 app goes through D3D11-on-12); the Python binding SpoutGL fills a numpy array, but inside Spout the receive is a GPU-to-CPU readback anyway. The Rust crate `spout-rs` sends an OpenGL texture or CPU pixels, not a D3D texture, so a wgpu game would read back, send, and be read back again. Sender and receiver must be on the **same adapter**; on two GPUs a receiver is blank or falls back to a CPU copy. Frame and pick would be two senders with no shared sequence number, and I found nothing saying it carries a 32-bit integer format.
- **Python cannot read a shared texture without ending in a CPU copy [V, I].** `ctypes` could call `D3D11CreateDevice` and the rest of COM, but there is no Python example of opening a shared resource, and the end of the road is a staging texture and a map, which is the readback again. CUDA's DirectX interop is NVIDIA-only and does not offer D3D12. pygame can only upload from the CPU (documented as slow, experimental); a zero-copy display needs OpenGL and a different library.
- **Two GPUs [V for the Direct3D 12 documents, not tested here].** A cross-adapter texture exists in D3D12 but lives in system memory, row-major, with GPU copies and shared fences, and Microsoft says it cannot be shared across D3D API versions, so a Python receiver cannot use it. The two adapters of the dev machine (RTX 3090, AMD integrated GPU) therefore could not share a texture without host memory in between, whichever route is taken. I did not test it.
- **Other roads [R, I]:** a named pipe with raw frames is lossless but adds a kernel copy; NDI and the OBS virtual camera are lossy, which destroys the pick map; screen capture of the window has no pick map and the yellow-border switch of Windows Graphics Capture needs a newer build than 19045.

**Recommendation (high confidence):** no GPU sharing. Read both textures back in the game (about 1 to 2 ms, measured above), write them into a shared memory block, and read it in Python. The frame and the pick map come from one submission and one slot, so they cannot disagree. The shape: a ring of 3 slots, each with a header (a sequence number that is odd while it is written and even when done, the frame number, width and height), the colour frame and the pick map; Python checks the number before and after its copy and tries again if it moved (a seqlock). Rows of a 1280 by 720 texture are already a multiple of 256 bytes in all three formats, so there is no padding to strip **[V, arithmetic]**. A cheaper variant reads back only a small box of the pick map around the cursor when asked, cutting 7 to 15 MB a frame to nearly nothing. Python's own copy of a 3.7 MB frame out of shared memory measured 0.12 to 0.46 ms in the agent's run and 0.46 ms in mine; a `numpy` view of it costs nothing. Python's `shared_memory` creates a named mapping on Windows that Rust's `CreateFileMappingW` with the same name should open **[I: the Rust side was not built]**; `unlink()` does nothing on Windows, the block lives until the last handle closes.

**Not verified:** the Rust-to-Python named mapping, real per-frame latency with a rendered (not empty) texture, Spout on this machine, the CuPy and PyCUDA surface, and D3D12 cross-adapter between NVIDIA and AMD.

Opinion (**medium confidence**, revised 2026-11-15: with the CPU hit of section B no frame has to leave the game, so A5's snapshot and all the sharing above wait until the owner wants VA to show the 3D view itself): A1 first. The game's window already shows the true render, so A3 buys one window at a real cost. Choose A3 or A4 later only if the owner wants VA's tools over the 3D view.

### B. How does a pointer become a tile pixel?

- **Revised 2026-11-15 after the owner asked why a pick map at all (it is a large feature with little reuse outside painting): B1 below is now the recommendation and B2 the option held back.** The first draft of this page recommended B2 and called B1 "not recommended" because two implementations of the tile mapping could drift. That weighed the risk too heavily: a test can lock the two together (see the oracle below), and B1's code is reused by gameplay while B2's is not. See "Alternatives to the pick map" at the end of section B.
- **B1, the CPU does it** (the owner's "shape of the mesh and the name of the texture"; **recommended**): a ray against the boxes of the voxels it passes (section E) gives the grid, voxel, face, the point on it and the normal; the face, the block's orientation (24), the slice of a slab or stair (D10) and the grid's own coordinates turn the point into a tile pixel. It repeats, once, the engine's mapping from a point on a face to a picture pixel; it does **not** repeat the relief (the exact pixel under the eye at an oblique angle with prisms or parallax occlusion is not what it names; it names the pixel of the true surface). It must also look at the pixel's alpha and continue the ray through a clear pixel of a cut-out (leaves), as the eye sees through it.
- **B2, the GPU says it** (the first draft's recommendation): the fragment shader writes a second output, the picture word and the pixel position in the tile **after** the relief shift, to a second render target. Only in a variant compiled in for the tool (the pattern of `pictures_on`/`pictures_off`), so a player's shader is byte-identical. The answer is the shader's own, so relief, orientation, slabs and ships are right by construction. Every screen pixel has an answer, so VA can draw a stroke in screen space and map each step to a tile pixel; a stroke crossing a block edge continues into the next block's tile pixels. Cost: 8 bytes a pixel of extra write, in the dev variant only (**not measured**).
- **B3**, the same shader rendered again for a 2 by 2 scissor around the cursor (a scissor, not a smaller viewport, so derivatives are right): less bandwidth but a second draw path, and VA could not draw a stroke in screen space. B2 is simpler.
- **Fallback with no GPU change:** the tool forces `relief flat` (a setting that exists) while painting, so a flat face is exact and B1 is enough. It gives up "with the relief on", so only a stopgap.
- **Does B2 work with any shader pack, even one built for nothing like this? Yes, with the interface as it is [read, `shader-pack-format.md`].** A pack defines one function, `pack_shade(Surface) -> colour`, and may bind nothing, declare no variable outside a function, and call no texture function. The engine's own shader owns the vertex stage, the geometry, the picture lookup and the relief, and it would write the pick output itself after `pack_shade` returns. So however far a pack's look is from the default's, it decides a colour and nothing it does can reach the pick output. (A pack that threw a pixel away would take its pick with it, which is right: you pick what is drawn. **[Not checked:]** whether `discard` is allowed in a pack; the page does not list it.) The sharing of one fragment shader for colour and pick is the point: the pick is the shader's own answer, not a copy of its logic.
- **Where B2 would stop working, and the rule that prevents it.** If a later pack interface lets a pack run its own passes, move vertices or warp the finished picture (the Aperture-style interface in `shader-systems-survey.md`), a pack could change where a pixel is without the pick output knowing. The rule to write into the shader pack spec now: **the pick target belongs to the engine's geometry pass and never to a pack; a pack interface that moves pixels must move the pick map by the same remap.** A shader pack written for another game that draws everything its own way is outside this interface today, and B1 (the CPU, below) is the only method that does not depend on the shader at all.
- Limits **[read]**: pictures are drawn only within the texture distance (64 voxels by default) and levels of detail above 0 carry none; beyond that the answer is "no picture".

### C. How does a change reach the game?

- **C1, files and a watcher:** VA saves the PNG, the game notices and reloads. Today the base pictures are inside the program (`include_bytes!`), and a picture reaches a client as part of the server's package, so a reload is "the integrated server reads again, builds a new package and sends it" (the `/reload` of the architecture review). That is the big piece, and it is semantic (block data can change).
- **C2, a client-side picture override** (**recommended**): the renderer gets `set_picture(word, pixels)`, which writes one layer and its mip chain of the existing array (a 16 by 16 picture has 5 levels). It is cosmetic: not in the package, not in the world, a replay is unaffected, the server never knows. VA pushes its pixels over the bridge as it draws, so unsaved strokes show live; Ctrl+S writes the PNG as it does today. The same override, read from a client folder, **is** the D9 texture pack, so a player gets a feature out of it, not only a developer. It must cover the companions (`_s` specular, `_n` normal with its height in alpha), or relief cannot be painted.
- The brush guide in A1 can be a temporary override too (the brush's pixels drawn at half strength over the tile), so the shader needs nothing for it.
- **Pack reloading** is its own plan, in `hot-reload-plan.md` (every kind of reload and the order to build them in). The picture override is its step 3, so this tool's first piece is built there, on the way.

### D. Who may run it

**Decided by the owner, 2026-11-15: mod cheating safety is not a concern for this tool.** The layers an earlier draft of this page listed (a cargo feature, a token, loopback only, no sending, a server's opt-in) are dropped, not built. One consequence stays, for engineering and not for safety: the tool's code is a client plugin and a dev variant of the shader, so it is easy to leave out of a build, and the pick output costs nothing in the variant a player's game uses.

### E. The CPU's side: a surface hit, and what a tractor beam needs

The owner's question: is the CPU ray-and-mesh code what a later tractor beam would need? **Mostly yes, but it is a different thing from the painting's pick, and the two should not be mixed.**

- **Today's ray finds a voxel, not a surface [read, `world_view/src/ray.rs`, `session.rs` `target()`].** `cast_ray` steps through voxels and stops at the first one `is_solid` calls solid; `RayHit` has the grid, the voxel, the voxel before it and how far along the ray it enters the voxel's cell. For a full cube that entry is the point on the face. For a slab, a stair or any partial shape (boxes in eighths of a voxel) the ray enters a cell it may not touch, and the point is wrong. There is no code that intersects a ray with a block's boxes (`block_models::Shape::boxes()` is there to do it with).
- **What a tractor beam wants is a point on the surface of the simulation's geometry, on the server, deterministically.** The hard rule (terrain and gameplay bit-identical on Windows and Linux, nothing from a GPU, the server draws nothing) means it cannot use the pick; it needs a Rust function: ray against a voxel's boxes, giving the grid, voxel, face, the point (in the voxel's own coordinates, so that it stays exact far from the origin) and the normal. A ship's grid is the same call in its own coordinates. For a beam that pushes a rigid body at a point, Rapier's own ray query against the bodies' colliders is another way to get a point and normal on a ship **[believed]**; nothing in the code uses it today. I did not check which fits better; it is the first question when the beam is designed.
- **The painter's pick answers another question: which picture pixel is drawn here.** With relief on, the drawn surface is an illusion above the true one, so the two differ by design: the beam should hit the true surface, the brush should paint the pixel the eye sees. One is exact for physics, the other for sight.
- **They can still check each other.** With `relief flat`, the CPU surface hit's picture pixel (face, point, orientation) must equal the pick map's pixel for every ray in a test. That locks the shader's mapping and the CPU's mapping together, and it is the CPU method that stays correct if a pack ever comes from outside the interface (the case where B2 stops working above).
- **A proposal (revised 2026-11-15):** build the CPU surface hit first, for the painter **and** the beam, with the return type above; it is the part with reuse (aim highlight, placing a block on a partial shape, projectiles, the surface under a foot). The cross-check test comes with it.

### Alternatives to the pick map (added 2026-11-15)

| | What | Reuse outside painting | Exact under relief and any pack? | Cost |
|---|---|---|---|---|
| **P1** | CPU surface hit (B1) | **high:** beam, projectiles, aim, placement on partial shapes | names the true surface's pixel, not the eye's at oblique angles; independent of every shader and pack | a ray against boxes, a mapping function, tests |
| **P2** | P1 with `relief flat` while painting | as P1 | exact (a flat face has no shift) | none beyond P1 and a toggle; the painter sees the relief off only while painting |
| **P3** | The oracle: one test picture whose every pixel colour encodes its own place (red the column, green the row, blue the layer), drawn unlit with `relief flat` and read back, to prove P1 names the same pixel as the shader | a test for the engine's mapping in general | the shader's own answer, as a **test**, with no shader change | a GPU test; no production code |
| **P4** | The pick map (B2) | low: editor selection, debug views, screenshot tests that say which tile is where; never gameplay (a GPU result cannot be used by a server) | yes, by construction, for any pack of the interface | a second render target, a shader variant, a readback, a sharing protocol |
| **P5** | The probe frame: for one frame replace every picture with an encoded one (as P3), render with a neutral pack and the scene lift at 1, decode the colours | none | yes, no shader change, but fragile: filtering, mip levels, the sRGB round trip and fog must all be proved to leave the code unchanged | two renders and a swap of every picture; a hack I would not build as a product |
| **P6** | A pick drawn only around the cursor (B3) | none | yes | a shader variant and a second draw path |

How large is the difference P1 leaves? **[Believed, arithmetic, not measured]** At the default relief depth of 0.1 voxel and a 16 pixel picture, the shift is about 1.6 pixels at 45 degrees off the face's normal and about 2.8 pixels at 60, and none looking straight at it. So P1 is a pixel or two off at a low eye with relief on, and exact looking at the face, which is how one paints. If the owner finds that a pixel or two matters, P2 removes it at once, and P4 is still there to build then.

## What it adds to Cave

Three pieces, each useful on its own, and a small crate; nothing else of VA's work (brushes, undo, colours, wrap-assist) moves into the game.

1. The CPU surface hit and its mapping to a picture pixel (section E), with the oracle test (P3); also what the beam needs. *(The pick output, a compiled-in variant, is held back: B2/P4.)*
2. `renderer`: the picture override (C2), which is also the texture pack.
3. A bridge (a client plugin that sends the pointer's tile pixel and the names table, and calls the override). With P1 and a view in the game's own window (A1), no frame and no pick map need leaving the game, so the sharing of frames in section A is not needed until streaming is wanted.
4. In VA, in Python: a socket client, the screen-to-tile mapping and the snapshot view.

A bonus **[believed]**: every voxel of dirt shares one tile, so a stroke at a block's edge shows on the neighbours at once. That is VA's wrap-assist, in the world, for nothing.

## Built so far (2026-11-16/17)

**Step 1, the picture override**: built as step 3 of `hot-reload-plan.md` (`VoxelRenderer::set_picture`, `--texture-pack`).

**Step 2, the CPU surface hit and its mapping, with the oracle (P1 + P3).** Built, tested, not yet used by any plugin. [run: every claim below]

- `block_models`: `Shape::first_surface(origin, direction, longest) -> Option<SurfaceHit { face, distance, point }>` walks the 8 by 8 by 8 sub-cells of a voxel and stops at the first filled one it enters (a ray over a bottom slab goes on; a stair's riser is met inside the voxel). Plain `f64`, no graphics card, so a server can use it (the tractor beam). `BlockTable::face_picture(block, state, orientation, face)` is the picture the renderer draws there. `FacePicture::place_of(point) -> PicturePlace { across, down }` (shares of the picture from the left and the top) and `PicturePlace::pixel(size)` map a point on a face to a pixel.
- `world_view`: `cast_surface(grid, start, direction, range, shape_of)` is `cast_ray` for partial blocks. Both now run on one `VoxelWalk`, so they cannot drift apart (the old `cast_ray` tests pass unchanged).
- `game_shell`: `Session::target_surface() -> Option<SurfaceTarget { hit, content (block, state, orientation), picture: Option<{ picture, place }> }>` over terrain, planets and ships. `Session::target` and `target_surface` share one `aimed_grids` (moved to `session/surface.rs`; the tests that use `target` pass unchanged).
- **The oracle (P3), on the GPU** (`renderer/tests/gpu_rendering/picture_places.rs`, run on both adapters of the dev machine, RTX 3090 and AMD integrated): a picture whose 64 pixels each have a colour of their own, shining by itself (so no light changes a colour), is put on all six faces of a block in all 24 orientations; where the card is aimed (at the middle of an eighth of a face, from a slant) the pixel it draws is the pixel `place_of` names, 1,152 probes a run. What a colour is is read off the screen (a head-on view of the unturned +z face, where red grows to the right and green downward), not from the code under test.
- **Mutation:** 17 deliberate breaks (the row, the negative way, across read as up, the face hit, the range, the point put on its plane, the order of the walk, a start inside counted, the far edge, a far voxel's start, the range of the surface walk, a hit with no ray, the picture list start, a ship's ray not turned, the farthest surface winning, orientation read as none for terrain and for a ship), each caught. The first run left four alive (the three place mutants were caught by the unit tests before the GPU test ran, so its bite was not shown until it was run first; the farthest-surface and both orientation mutants had no test; the picture-list start needed a block with state colours); tests were added and all are caught.

**What it does not do (yet):** (1) it does not look at a pixel's alpha, so the ray stops at a leaf's clear pixel where the eye sees through it (it needs the picture's pixels on the CPU: the client has them in the package); (2) a ray that starts inside a partial voxel ignores that voxel, as `cast_ray` does; (3) with a relief (prisms, parallax) the answer is the true surface's pixel, a pixel or two off the eye's at a slant (P2 `relief flat` removes it); (4) the surface hit is on `Session`; the client plugin's context (`ClientContext`) does not give it yet, which is step 3 (the bridge); (5) nothing measures its cost: it is one ray a call.

**Steps 3 and 4, the bridge and VirtualAtlas's side (2026-11-17), with the owner's answers to the three questions: all the defaults (A1: the game's window is the view and VirtualAtlas a second window; edits live in the painter's client only; colour pictures first).** The owner also asked that VirtualAtlas stay game-agnostic, so that any game that speaks the protocol can use it. **My choice, to confirm: a neutral protocol and no plugin system in VirtualAtlas.** The one place a game and the tool must agree is which file a game's picture is, and the protocol gives that to the game (a picture is told as an id and the names of the files it may be, the first that exists is used); with that, nothing in VirtualAtlas is about one game, and a plugin system would have no second thing to plug. If a game needs something the protocol cannot say (a tool of its own in VirtualAtlas's window, say), a plugin point is the next step, with that game as the reason.

- **The protocol** is `tools/virtual_atlas/BRIDGE.md` (version 1: JSON lines over loopback TCP; VirtualAtlas listens with `--bridge [PORT]`, the game connects). The game says `hello`, `tiles` (id, file names, size, group) and `pointer` (tile id, pixel on the picture repeated in every direction, buttons, a segment number); the tool says `welcome`, `known`, and `tile` (the pixels of a picture whenever it changed).
- **VirtualAtlas** (one file still, a new section "The bridge"): the editor gained `external_press` / `external_move` / `external_release` (the same code path the mouse takes: a press now goes through `_press_pixel`), a `BridgeController` (messages to edits and back, no socket in it), a `BridgeLink` (loopback socket, nothing blocks) and `--bridge`/`--group`. A pointer over a tile selects it alone and turns wrap-assist on, since a picture repeats on every face that has it, so a stroke that runs off one face onto the next goes on and comes back in on the other side. [run: 36 new tests, 716 in all; 29 deliberate breaks of the bridge, each caught after two tests were added.]
- **The game** (`engine/game_shell/src/paint_bridge/`: protocol, base64, connection, catalogue, path, painter; `Session::target_surface_toward`; `Camera::direction_through`; the command `.paint [PORT|off]`; `windowed.rs`): in paint mode the cursor is free, the left and right buttons are the tool's, the middle button and a drag turns the view, and each frame the pointer's ray (through the cursor, not the crosshair) is the surface hit of step 2, which becomes a pointer message. The tool's pictures are written with `VoxelRenderer::set_picture`, keeping the picture's own companions (a picture the tool sends has none). The path makes the pixels continuous along a flat run of voxels (the renderer's own coordinate before its fraction is taken) and starts a new segment where the surface turns. Client only: the server and a recording never know.
