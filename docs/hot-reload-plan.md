# Hot reloading in every way Voxunami will support it: an order of steps

**A proposal; nothing here is built.** Written 2026-11-15 on the branch `graphics-world-painting`, at the owner's request ("hot reloading in all the ways Voxunami will support it, in whatever order is best for the health of the project"). Marks: **[read]** read in the code or a document, **[believed]** my reasoning, not run, **[measured]** run.

## What can be reloaded, and what a reload touches

Two things decide how hard a kind of reload is: **who sees the change** (only this player, or the world) and **whether a recording has to know**. A recording carries the package and then the server's stream, so anything the server changes after the join is a thing a replay must be able to show again **[read: `protocol-and-replay.md`, the package is in the Welcome]**.

| Kind | Where it lives today | Who sees it | A recording must know? | Exists today |
|---|---|---|---|---|
| Shader pack files (`lighting.wgsl`, `pack.json`) | a client folder `shaderpacks` | this player | no | read once at start; `.shader NAME` switches live and a refused pack is taken off again **[read]** |
| Shader pack settings (`NAME.settings.json`) | beside the pack | this player | no | read once at start **[read]** |
| The engine's own shaders (`voxel.wgsl`, `pictures_on.wgsl`, `relief_*.wgsl`) | `include_str!` into the program | this player | no | none; a developer rebuilds **[believed]** |
| Pictures (tiles and their `_s`, `_n` companions) | base pictures are `include_bytes!`; a pack's are in its `textures/` | this player, if the change is client-side | no, if it stays a client override | none; texture packs (D9) are specified, not built **[read]** |
| Block data (blocks, patches) | the base blocks' JSON is `include_str!`; a pack's is on disk | the world | **yes** (it changes the package) | none; "packs are read once at start" **[read: `architecture-review.md`, F3]** |
| Bodies (planets, moons) | a pack | the world | yes | "a body in a pack reaches only a new world" **[read]** |
| Terrain generators | code, by version | the world | yes | **never reloaded**: a generator version is a file format, so a changed one is a new version |
| Rules of server plugins | compiled Rust | the world | yes | none, and compiled Rust cannot be (the WASM stage, `architecture-review.md` M4, is where it could be) |

## The order I recommend

The rule behind it (**medium-high confidence**): first what only this player sees, which touches no protocol and no recording; then what changes the package, which needs a decision about recordings first; last what needs a new runtime. Inside each, the smallest blast radius first, and each step is the first user of a piece the next one needs.

**Step 0. The spine, with no behaviour of its own.** One small module in `game_shell` that every kind uses: *a source* (a folder or a file), *a fingerprint* (modification time and size, then a hash only when those moved, polled a few times a second, so there is no new dependency; `notify` would need a licence check), a *settle* (a file counts as changed when it has not moved for about 150 ms, because editors write in two steps and a half-written file must never load), and a *result* (reloaded, or failed with the reason). Its one rule: **load everything beside the old state, and swap only when all of it is good**; a failed reload leaves the game as it was and says why in the chat. The shader packs already have half of that (a refused pack is taken off again). Tests first, on a fake source: a half-written file, an error, a change during a reload, two changes in a row. The command: `.reload [kind]` by hand, and `--watch` to do it on change (off by default). *Why first:* it is small, it is the same code in every later step, and a bad one would be copied six times.

**Step 0 as built (2026-11-15): `engine/game_shell/src/reload.rs`.** [run: 32 tests; 9 deliberate breaks of the code (no settle wait, a touch counted as a change, nothing remembered between looks, the accepted files not updated, a swap after a failed load, no interval, an unreadable folder told at every look, polling while not watching, removed files not told) each fail at least one of them.] What exists: `Watcher` over a `Source` (`DiskSource` for a folder or one file, ignoring hidden, `~`, `.swp`, `.tmp`, `.part` and `#lock#` files), `Reloadable` (a `load` that cannot change the state in use, then a `swap`), `reload_once`, and `Reloads` (the kinds, `.reload [kind]` as `reload(name)`, `--watch` as the `watching` flag). Time is given to the watcher, never read, so every timing is tested exactly. Not wired to anything: **the `.reload` command and `--watch` come with step 1**, because with no kind there is nothing for them to run. Three facts found while building it:
- The clock that stamps files is coarse. [measured on this machine, Windows 10 NTFS: 196 of 199 back-to-back writes of one file had the same modification time; steps of 1, 7 and 8 ms were seen.] So the stamp alone can miss an edit that keeps the length and lands in the step of the last read. The watcher reads a file only after its stamp has been still for the settle time (150 ms), which is longer than a step, so after the start it cannot be caught so; the start (`Watcher::new` reads at once) is the one exposed moment.
- Reading a file to tell a change from a save with no change is done only for files whose stamp moved (a test counts the reads), so a folder of hundreds of pictures costs one scan of stamps per look. **Not measured** on a real folder of hundreds of pictures; do it when step 3 has them.
- The game writes its own settings files (`NAME.settings.json`, in the same folder as the packs). Step 1 must expect its own write to be seen as a change: a reload of what is already in use is harmless but should say "no change" and not redraw.

**Step 1 as built (2026-11-15): shader packs and their settings** (`view.rs`: `read_shader_packs`, `swap_shader_packs`; `windowed.rs`: the kind `shaders`; `.reload [kind]`, `--watch`). [run: 9 tests with a stand-in renderer; 6 deliberate breaks of the swap each fail one; and a real Cave window with `--watch` while a pack file was edited under it: a good edit reloaded in 84 to 411 ms, a pack with a loop in it was refused with the reason and the old pack stayed, and fixing it reloaded again.] The first live run found a defect the tests did not: a broken pack is not on the shelf, so the reload took it for a deleted pack and went back to the game's own shader. Fixed (a chosen pack that cannot be found while something is wrong is kept as it was) and tested. What a reload does: reads every folder again like a start, hands the renderer the chosen pack with its settings first (it makes nothing if they are what it has), and replaces the packs, the names, the choices and the files of settings only if the renderer took it. The game's own writes of `NAME.settings.json` are seen by the watcher and are no change (tested), so they print nothing. **Not done:** the property "pictures after a reload are byte-identical to pictures after a fresh start" (the renderer's own rule makes the shaders from the pack's text and values alone, which is the reason I believe it; not run); the engine's own shaders (step 2); a pack folder that did not exist at the start is not watched.

**Step 2 as built (2026-11-15): the engine's own shaders** (`engine/renderer/src/engine_shaders.rs`: `EngineShaderTexts`; `VoxelRenderer::set_engine_shaders`; `view.rs`: `use_engine_shaders_from`, `swap_engine_shaders`; `windowed.rs`: the kind `engine-shaders`; the option `--engine-shaders DIRECTORY`). [run: 6 + 4 tests on the text and the swap; 3 tests on every adapter that draw with an edited shader (a halved colour), refuse a shader the shader language refuses, and give the program's own text back to the pixel; 6 deliberate breaks of the code each fail a test (two of them first survived, because the test of "a pack chosen afterwards" used a pack the renderer takes as no change, and no test gave a refused text a second time; both tests were made stronger and the two breaks are caught; the harness had also left a stale build, since a file put back keeps an old time stamp and cargo took it as built: touch it after); and in a real Cave window with `--watch` on a copy of the shaders: a good edit reloaded in 330 ms, an edit with a name that is nowhere was refused with the line and the reason and the old shader stayed, and the fix reloaded in 322 ms.] The 15 files the voxel shader is made of (`voxel.wgsl` and its kinds) were `include_str!`s in one function; they are now a struct of 15 texts, the program's own (`built_in`) or a folder's (`read`: every file or none, the missing one named). A test holds the texts of all 36 kinds of the shader to the byte against what they were before the change (a fingerprint taken from the old code), and another that the files of the source folder are the program's texts. A **picture** made from a copy of the files is the same file, to the byte, as one made by the program (measured: screenshots with the same hash), so the flag changes nothing until a file is edited.

How it is used: `--engine-shaders engine/renderer/src` reads the shaders from the source folder instead of the program (at the start, and again on `.reload engine-shaders`, or by itself with `--watch`; `--screenshot` and `--benchmark` take it too, and then a failure is an error, since a picture made with other shaders than were asked for is a lie). It watches only the 15 files, so an edit of the Rust beside them is no change. A reload that is refused (the shader language or the card) changes nothing and tells the reason; the line numbers are those of the file where the error is in `voxel.wgsl` (it comes first in the text), and are counted from the start of the combined text for the others. The shader pack in use and its settings stay; a pack chosen afterwards is made with the edited engine shaders. **Decision to confirm with the owner:** the flag is **not** left out of a player's build (a cargo feature would leave its code unchecked by the gate, and the folder has to be named by hand); a player who names a folder can hang their own graphics card with a loop, and no one else's. **Not done:** `crosshair.wgsl` and `overlay.wgsl` (each is its own small shader, made at the start); the pack's own error lines are counted from the program's text, not from an edited one; a shader that is good for the shader language and wrong in what it draws is not told by anything.

**Step 3 as built (2026-11-15): pictures, client only** (`renderer`: `VoxelRenderer::set_picture`, `PictureWrite`; `game_shell/src/texture_pack.rs`; the option `--texture-pack DIRECTORY`; the kind `pictures`). [run: 5 tests on every adapter and 14 on the folder and the swap; 10 deliberate breaks of the code each fail a test (one, writing over the wrong layer, first survived because every test had a size with one layer; a test with two was added, and one mutant first "failed" only because it did not compile); and a real Cave: a folder holding the world's own pictures draws the world's picture **to the byte** (screenshots with the same hash), a folder of magenta pictures turns the terrain magenta, and in a real window with `--watch` a picture added, changed, damaged and deleted each reloaded in 2 ms with the right words.] **Renderer:** `set_picture(class, layer, &PictureWrite { rgba, specular, normal })` writes one picture and the levels of smaller pictures under it into its layer of the three texture arrays, the same bytes that giving it at the start puts there (they are made by the same code), so a renderer that was given a picture this way draws as one that had it from the start, near and far, with companions (tested to the pixel on every adapter). A companion that is `None` clears the one that was there. A picture that is not as big as its place, or a place that is not there, is an error that changes nothing. A picture that gains or loses a relief changes its word in the palette (the prisms leave a face alone unless the word says it has relief), so the palette is made again then. **Client:** `--texture-pack DIR` reads `DIR/NAMESPACE/textures/NAME.png` (`stone_top.png`, `stone_side.png`, `stone_bottom.png`, or `stone.png` for a face with none of its own; `_s` and `_n` companions) for the faces of the blocks whose base name is `NAMESPACE:NAME`, and writes each into the place the world has for that face. A face the folder has no picture for keeps the world's. A picture the folder lost goes back to the world's. **A file that is there and no good (not a PNG, the wrong size) keeps the picture as it was** and is told; this is what an editor halfway through a write, or a painting tool, needs. The replaced picture takes its companions with it (the world's belonged to the picture that is gone); a companion with no picture of its own changes only that companion.

**Choices of mine to confirm:** (1) the folder is one texture pack named on the command line; the ordered list of D9 (several folders, later over earlier, the server's pictures as one movable entry) is **not** built, and so is not the player's saved order. (2) Two faces the world draws with one picture have one place; if the folder gives them two different pictures the first (top, then side, then bottom) is used and the other is told. A full answer is per-face pictures in the world (a package change). (3) The plan said "a flag reads the base pictures from the source folder instead of the program": **not built**, because a folder with the namespace `base_blocks` (`base_blocks/textures/grass.png`) does the same for a developer, with the same code. **Not done:** `terrain_version` is raised by a write so that shadow maps are drawn again for a cut-out picture, but no test looks at that; a package that changes while the client runs (none does today) would need the pictures put in use again; the texture packs of `block-textures-spec.md` D9 names in the spec (`texture_packs/<name>/...`) are one folder here; the cost of watching a folder of hundreds of pictures is **not measured** (the watcher reads a file only when its time stamp moves, so a still folder costs one scan of time stamps per look).

**Step 4 as written (2026-11-15): `specs/package-replacement-spec.md`, a proposal for the owner to decide; no code.** It compares five options (a message that replaces the package; a second `Welcome`; disconnect and rejoin; no live reload; telling no one) and recommends **a message, `PackageReplaced`, protocol version 12** (medium-high confidence), sent first in the tick to every client, with the appended registry entries and the new package, applied by the client with the tick, and a replay that needs no change. **A correction to this plan:** the option "refuse a reload while a recording is made" is not one a server can take, because a recording is made by the client and the server cannot know; only a singleplayer process that is both could, and I drop it. Four questions for the owner are at the end of the spec (the message or a second `Welcome` first; a bad replacement stops the client; every mesh made again first; a block that disappears stays as missing content). **Step 5 waits for the answers.**

**Step 5 as built so far (2026-11-16): the client half, and nothing that sends it.** Your answers to the four questions of the spec were all yes (the message first, a bad replacement stops the client, every mesh made again first, a vanished block stays as missing content). **Built and tested, committed in its own phase: the protocol message `PackageReplaced`, version 12** (`engine/protocol`: the layout pinned byte for byte, one spelling: registries in order, none empty, no entry twice); **the translator's growth** (`world_storage`: `SourceTranslator::append_content` and `check_append`, so a source's registry table, and the numbers it maps to, grow); **the client's rules** (`engine/client`: the program is asked to grow its registries only after the whole message is known good, the numbering check is worked out again, `poll_tick_with`, `ClientEvent::PackageReplaced` first in its tick); **the session** (`game_shell`: the package, table and meshes are built beside what there is and swapped in only if all of it is good; a block gone, a block added that was not appended, an unreadable package, a table the renderer cannot draw each stop the session with the reason and leave what it had; the terrain and ship meshers are made again with the new table, the renderer is told the ships are gone and told of them again, the player's own ambient light is kept, the window draws with the new palette and writes the `--texture-pack` pictures over the new textures again); and **replay equals live across two replacements** (a scripted server, a recording of it, a replay in `Mode::Replaying`: the package, the table's colours and the view summary equal after every tick). [run: 8 + 3 + 6 + 3 + 6 tests; 17 deliberate breaks each fail a test (the first run found three gaps: no test that a refused message grows nothing, none that the digest check is worked out again, and none that the terrain's mesher is the new one; all three were added).] The pinned recording of the standard session changed in its checksum alone, for the version byte (with the version set back to 11 the old checksum came back). **No server sends the message yet.**

**Why the server half is not built, and what I found (a piece riskier than the plan said).** A survey of the server (made by a read-only agent, then the key claim re-read by me) found that **ten plugins of Cave each keep their own copy of the block table**, taken when they were built (block editing, items, fire, light and multi-scale light, movement, ship commands, docking, grid bodies, grid lifecycle), and the plugin interface has **no hook to tell a plugin that content changed** and builds its plugins once. Besides the copies: (1) the collision caches (`BlockCollisions`) are keyed by the model number of the table, and **the table puts the unknown block's model after all the blocks, so appending one block moves it** (read: `block_models/src/table.rs`, the unknown base is pushed last): a stale entry would make a new block a full cube; (2) the colliders and masses of ships are made again only when a brick is edited, so a changed shape or density would stay stale; (3) the light that was worked out and the cache of cells (`contents_known`) go stale when emission or opacity changes; (4) the items of placeable blocks are registered once into the entity catalog, so a new placeable block would have no item; (5) the property handles are column numbers, valid only if the schema is unchanged; (6) `ContentPackage::apply_packs` is meant to run once before a world loads, and applied again would patch patched blocks twice; and the server's registry is lent out once, so a reload must run on the tick thread. **My recommendation is to build the server half in two parts, and to ask you first which:** (A) *appearance only*: a reload may change colours, pictures, ambient light and the names and appearance of new blocks, and **refuses with a list** a change to anything the server reads (shape, opacity, density, emission, flammability, passability), which needs one new `Server::replace_package` and a content-replaced notice that only the base game's loader answers, and no plugin's table is touched; this is the common edit of a modder and of the painting tool, and every claim above that is not about shape or properties does not apply to it; (B) *everything*: a notice every plugin answers and the caches cleared, which is a refactor of ten plugins and their tests, with the risks above, that I would do as a plan of its own. **A new block with no item (4) is true for both** and is a decision of the game's. The server also needs the base game read as a pack by a development flag (`architecture-review.md` F3) for an edit of a base block to show; the plan's own condition for step 5.

**Step 5, server half: the owner chose B, everything (2026-11-16). Built in four phases: pin, share, follow, send. Phases 1 and 2 are done.**

*Phase 1, pin what the rules read of the table (done).* Before changing who holds the table, a survey of what the tests depend on. **Step 6. Bodies (planets and moons).** Today only a new world sees them. Either leave it so and say so in the reload's answer ("applies to new worlds") or build the in-place change that `planetary-mass-change.md` looks at. I would **leave it, with the message**, until something needs more.

**Step 7. Rules of plugins, when the WASM stage exists.** Reload at a tick boundary; the plugin's saved state (the saved sections the host already writes, sorted by identifier) is what carries across; a module that fails to load or to read its state is not swapped. It is the one kind where a design made too early would be wrong, so it waits for the runtime and is only listed here so that the WASM host is built with "reloadable between ticks, state through the saved section" as a requirement, not found out later.

**Never.** Terrain generators (a released version is a file format), and a plugin in compiled Rust.

## Why not another order

- *Block data first* is what a modder wants most (`A6`), and it is the biggest step: it changes the package, needs the decision about recordings, and needs the base blocks as data. Done before steps 0 to 4 it would build the spine and the decisions for the first time inside the hardest step.
- *Pictures before shader packs* is just as safe; shader packs go first because the apply path exists and the owner needs it daily.
- *Step 2 before step 1* would be a nuisance for no gain: the pack path is what step 2 reuses.

## What I did not check

- That `discard` in a pack's `pack_shade` is or is not refused (`shader-pack-format.md` does not list it).
- How long a shader rebuild takes, and how Windows editors write files (the settle time of 150 ms is a guess, to be checked against the owner's editor).
- That polling modification times is cheap enough for a folder of many pictures (a few hundred files **[believed]**; step 0 should measure it).
