# Procedural materials: palettes, ids and secrecy (a discussion, owner's intent 2026-11-25)

The owner's intent, condensed from 2026-11-25: **each new planet a player reaches should have materials (block types) that exist nowhere else in the universe.** A material has properties (density, toughness, hardness, friction, impact elasticity, visual roughness, visual metallicity, light brightness, and others) generated from a seed; its texture is a blend of authored textures and noise layers, also controlled by a seed. The owner is not certain, but thinks **the server should never send the seed to a client, only a generated pack.** The aim is **markets**: a player who explores far finds a material with a wanted look or property and sells it, which fails if holding a block of it lets anyone find where it came from. The owner thinks the server should hold **several seeds, some used to make others** (a planet's seed), so that cracking one does not give away the more important ones. The owner asked for a discussion of why bricks have palettes, whether they are limited, whether blocks should be string ids everywhere and how Minecraft does it, and for research on seed cracking with a review of the plan. **A discussion and my opinion; nothing in it is built.** The research is `seed-secrecy-survey.md`. Marks: **[read]** in this repository; **[measured]** by the probe in `spikes/seed_probe/` (one machine, Windows); **[web]** read on the web (the survey says how); **[recalled]** from memory; **[believed]** my reasoning, not run. The item system is not touched by anything here, and I have not read it.

## 1. Why bricks have palettes **[read, measured]**

A brick is 32 x 32 x 32 = 32,768 voxels and holds one *channel* of `u32` values for each thing a voxel has (block, state, light levels). Each channel of each brick is held in one of three forms that the code switches between by itself: **uniform** (every voxel the same: one value, no per-voxel storage), **paletted** (the list of the distinct values, in order of first appearance, and a 1, 2, 4 or 8-bit index for each voxel), or **dense** (a `u32` for each voxel, once there are more than 256 distinct values). The saved and sent form is canonical: equal contents give identical bytes whatever form the storage was in (`engine/voxel_grid/src/channel_storage.rs`, `encoding.rs`).

**The reason is size, and it is large.** The block channel of 1,152 bricks of Cave's rolling hills (12 x 12 x 8 round the origin): 452 are uniform (nothing in memory, 5 bytes saved), 700 hold two to four values (4 to 8 KiB), none more. A brick takes **4,973 bytes** on average; with no palette it would take **65,536** (a `u16` a voxel) or **131,072** (a `u32`): **13 and 26 times more**, 5.7 MB for these bricks against 75.5 and 151.0 MB. **[measured]**

Reasons beside size **[read]**: a query asks the palette and not the voxels (`may_hold`, `indices_where`, `uniform_value`: a brick holding a ship of a few voxels costs a pass over its packed words, not a look at each of 32,768); each channel compresses on its own (a uniform light channel costs nothing beside a varied block channel); and the palette entry is a full `u32`, so **how content is numbered never widens the cost of a voxel**. Minecraft's chunk sections do the same for the same reasons: a palette of 4 to 8 bits for each section, a global one past that **[web: wiki.vg and a newer protocol mirror]**.

## 2. The limits **[read, measured]**

| What | Limit | Where | Past it |
|---|---|---|---|
| Distinct values in one channel of one brick | **256** paletted (8-bit index); more is dense | `MAXIMUM_PALETTE_LENGTH` | **a cliff in size, not a failure**: 257 distinct values take 131,072 bytes, 3.9 times the 33,792 of 256 **[measured]** |
| Distinct ids in the world | `u32`: 4,294,967,296 for a registry | `RuntimeId` | a panic on the 2^32nd entry |
| Channels in a layout | 65,536 | `MAXIMUM_CHANNEL_COUNT` | an error |
| Materials the renderer draws | **1,048,576** (`MAXIMUM_GAME_MATERIALS`; a choice: a quad carries 24 bits, 16.7 million) | `voxel_renderer.rs`; a GPU buffer of 16 bytes each, 16 MiB | an assert; a value past the palette draws magenta |
| Pictures | **4 sizes x 256 = 1,024**, and 8 MiB of pixels in a package | `block_textures.rs`; `block_models`: `MOST_TILE_SIZES`, `MOST_TILES_OF_A_SIZE`, `MOST_TILE_BYTES` | refused when the package is made |
| What a client is told at join | **every** block and picture of the package, in `Welcome` | `Welcome::package` | |

- `design-decisions.md` still said the renderer's palette cap was 256 material values; it has been a buffer of 1,048,576 since phase 31. **I corrected the line.**
- **What this means for materials** **[believed]**: a brick that holds the twenty materials of one planet is an 8-bit palette (about 33 KiB); only a brick of 257 or more different materials (a player's collage) goes dense. The id space is not a limit. **The first real ceilings are the pictures (1,024 at once: twenty materials a planet is 51 planets' worth, if every material has its own picture) and what a client is told at join (everything).** A client cannot be sent every material of a universe; section 6.

## 3. String ids: ours, Minecraft's, Luanti's **[read, web]**

- **Ours [read].** A `NamespacedId` is `namespace:name`, each part starting with a lowercase letter and holding lowercase letters, digits and `_`, at most 64 characters; the namespace is the plugin or pack that owns the content. **At rest**, the world file's `engine:registries` lists each registry's identifiers once, in file-id order, and bricks hold those file ids. **In memory**, a `RuntimeId` is a dense `u32` in registration order, "meaningful only within one run of one process"; loading maps names to this run's numbers, and a name whose plugin is missing becomes a placeholder, kept byte for byte. **On the wire**, a client learns the same numbering from the world description and from `RegistryAdditions` ("a registry only grows, so the client gives each the next number").
- **Minecraft [web].** Before 1.13 (the Flattening) blocks were numbers with a 4-bit data value; since then they are `namespace:name` ids with properties (block states), "removed numeric IDs" and the data value "replaced by a property and value system" (minecraft.wiki). A chunk save holds a palette for each section of block-state entries (a name and properties; the key names are recalled) and indices into it. The numeric state ids are **not stable between versions** ("not guaranteed to be the same"); with mods, Forge synchronises registries at login and refuses a client that lacks entries (forum threads, not primary). **[recalled]** The numbers are made at start-up from registration order, and before the Flattening there were 4,096 block ids, which is why mods fought over numbers.
- **Luanti [web].** Each map block (16 x 16 x 16) carries its own table of content id to node name (a version byte, a count, then a 16-bit id and a length-prefixed name for each, in the 5.4.1 source), so a block can be cut out and understood anywhere.
- **Where the strings go.** Minecraft and Luanti put names in each section or block; **we put them once in the file.** Ours is smaller (a name is 20 to 40 bytes and a palette entry 4) and gives up that a brick can be understood on its own; we do not need that. All three do the same thing: **strings are identity at rest and in negotiation; numbers are handles in memory and in flight.**
- **Should blocks be string ids everywhere? No for anything per voxel or per brick; yes for identity at rest and at negotiation, which is what we have.** **[believed]** A string compare in the mesher's loop over 32,768 voxels is a pointer chase against a `u32` compare, and 20 to 40 bytes would be sent where 4 do, in every brick. What the numbers cost (they change between runs and plugin sets) the table already pays.
- **What changes for procedural materials is the name and the table's size, not the layering.** (a) "The namespace is the pack that owns it" cannot name a material a world made. **Proposal [believed]**: a namespace reserved for what a world generates (`world`), and a name that is `m` and 32 hex digits of a keyed hash (33 characters, starts with a letter: valid as it is) so that it carries nothing. (b) The table holds every material ever made: a million materials is 34 MB of names alone, so a client is never sent the table (section 6).

## 4. The plan as I understand it (please correct me)

1. A planet gets materials of its own when it is first reached (the moment is yours to define). 2. A material is a block type whose properties come from a seed, and whose picture is authored textures blended with noise layers from a seed. 3. The server never sends a seed; it sends a generated pack. 4. The server holds several seeds, some made from others. 5. The purpose is a market: a block in hand must not lead to its planet.

## 5. Review against the research (`seed-secrecy-survey.md`)

### 5.1 What holds

- **H1. Compute on the server, send outputs.** A crack needs a public map from the secret to something seen. If the map runs only on the server and clients get results, the attacker's handle is the results, and with a keyed hash underneath they say nothing about the key; it holds even if a weak spot exists inside (survey 4.4). **Right; keep it.** Confidence high.
- **H2. A hierarchy.** Making a planet's key from a bigger one with a one-way function is how key derivation limits what one leak shows (survey 4.2). **Right, under C1 to C3.** High.
- **H3. Several secrets** limit the damage of a leak, but the way to have them is **several derivations of one big root, not several stored seeds**: a derived key is as independent of its siblings as a stored one if the hash is sound, and there is nothing more to store, back up or lose. Medium-high.
- **H4. "Never send the seed" is consistent with the engine only for the material layer.** Clients make terrain from the world's seed and each planet's seed (public in the recipe by design **[read]**), and cracking those is moot. **So there are two kinds of seed with opposite rules; the plan should say so.** High.

### 5.2 What has to change

- **C1. Never derive a secret through the engine's hash.** **[measured]** `terrain::mix` is a bijection; a child seed made with the engine's lattice hash gives its parent back in **about 6 ns**; one full-precision property made with the engine's value noise gives its seed back in **about 40 µs** (two runs each: 5.7 and 7.1 ns, 39.2 and 43.0 µs). A "hierarchy of seeds" made the way every other hash in the engine is made protects nothing. Every value that depends on a secret goes through a **keyed cryptographic hash**, which is **BLAKE3** (its `keyed_hash` and `derive_key` modes; decided, section 8, question 2), fixed-width inputs, a distinct purpose for each use. The engine's noise runs only on values that may be public (C3's "door"). Fatal if missed, cheap to do. High.
- **C2. A secret is big, random and from the operating system.** At least 128 bits (the root can be 256), drawn from `OsRng` (which `identity` already uses); never the world's 64-bit header seed, never typed by a person (a typed seed is a *shared* one: fine for terrain, not for the root). **[measured]** A 32-bit secret fell in 26 s through BLAKE3 on 12 threads; 64 bits is 26 years of a top GPU or 10 days of a thousand; 128 is out of reach (survey 4.1). High.
- **C3. Terrain seeds and material keys are different branches of the tree.** A planet's terrain seed goes to every client; if a material key were made from it, or from anything a client has, the client could compute the material. So `root -> terrain seed of planet n` (the client gets the *output*, one-way) and `root -> materials key of planet n` (never leaves the server) are siblings. A client may then know any number of terrain seeds and have nothing of the root or any materials key. **The door**: the step from a key to a leaf value (`PRF(material key, "texture") -> u64`) is one-way, so below it the engine's fast, invertible noise is fine, since recovering the leaf from pixels gives only the leaf. High.
- **C4. Ids carry nothing, and order carries as little as can be afforded.** Opaque ids from a keyed hash (section 3). **Order** is the quiet leak: a dense registry numbers things in the order they were made, so the materials of one planet are consecutive; a client that holds two materials with consecutive numbers has learnt that they share a planet, and which came first. **[read: the registries are dense and append-only; believed: the leak]** It reveals *grouping*, not origin, so I rate it low-medium. Options: (a) accept it in version 1 and write it down as a known leak; (b) number for each client (the server translates a brick's palette per client, which costs the "encode once, send to all" path). **My pick: (a), and never show a number to a player.** Low-medium confidence.
- **C5. Nothing answers a question about a place the client is not at.** No scan, no map entry that names a material, no "which planet has this". An oracle makes C1's search unnecessary. A scanner as a game feature should cost something and give a *kind* of hint, never a definition. High.
- **C6. The secret has a place of its own, and nothing that describes, copies or records includes it.** Today the world description sent to every client holds the world's seed and every recipe **[read]**. The root needs a **withheld section** like a pack's `server/` files; `describe` never includes it; **a world replicated to a client carries no root** (a copy of a multiplayer world has the discovered planets and not the undiscovered ones); recordings hold only what was sent; logs never print a key. **Make a leak a type error**: a `SecretKey` with no `Debug`, no `Clone` outside its module, no encoder in `protocol`, clearing itself on drop (`zeroize` is already in the tree **[read]**). And a **canary test**: a world with a known root, a session with recording, and a scan of every byte sent, described, saved outside the withheld section and recorded, for the root and every key derived from it; a mutation that puts a key in a message must turn it red. **[believed]** Cheap, and it makes a silent leak loud, as your standing rule asks of self-checks.
- **C7. Make once, then save the definitions.** A generator is a file format; materials made from code that later changes would move. When a planet is first reached the server makes its materials and **saves their definitions in the world** (data, like override bricks); the root is for *undiscovered* planets only. Numbers are made from integers: block properties are integers with a declared range already (below, section 6) and a picture's channels are 8-bit, so PRF bytes map to them by integer arithmetic and two servers of one world agree. High.
- **C8. Gameplay randomness never comes from a secret.** `lattice::voxel_random(seed, tick, grid, voxel, purpose)` hashes the world seed with `mix` **[read]**; fine, because that seed is public. A secret given to it as `seed` would leak by Randar's mechanism (survey 2.2): what players see would be a function of the state. C6's type stops the mistake, since a `SecretKey` is not a `u64`.

### 5.3 What the plan does not say yet, and I would decide before building

- **M1. What a client may learn, as a rule.** My pick: **a client learns a material only when it sees or holds it** (a brick that has it comes into view, an item made of it enters its inventory). It is a product rule that decides protocol and saves; added later it is harder than started from.
- **M2. How a planet's kind shows in its materials.** If a planet's temperature or class feeds the properties (volcanic planets: dense, glowing), a buyer narrows the origin to *kinds* of planets. That is information of a lower grade than identity, and may be the fun (hunting a kind) or the leak; **a dial** for how much of a property is drawn from the planet's public attributes and how much from the secret. Yours to set.
- **M3. Where veins lie is public.** Clients make terrain from public seeds, so where "slot 3" lies on a planet whose seed a client knows is computable without a visit; only what slot 3 *is* is secret. Scouting by shape is free; by substance needs a visit. To hide even the veins, terrain would have to come from the server as bricks (`GridContent::Bricks` exists for ships), at a bandwidth price. **[read, believed]**
- **M4. The operator sees everything**, so a server owner who trades has the whole universe. Governance, not engineering.
- **M5. Outside the engine**: coordinates in chat or screenshots, logs, "first finder" announcements, a trade right after a trip. Cryptography cannot help.

## 6. A design that follows the rules **[a proposal, believed]**

```
root (256 bits, from OsRng, once, in the withheld section only)
 |- terrain branch   -> terrain seed of planet n (64 bits)  -> in the recipe: PUBLIC, every client has it
 |- materials branch -> key of planet n -> key of material i -> properties, texture leaf seed -> PUBLIC once the client meets the material
 '- ids branch       -> id of material i (128 bits, `world:m<32 hex digits>`) -> PUBLIC, opaque
```

- **A material is a block**: an entry in the block registry, created at run time, with the properties as block properties: **values by namespaced key that plugins declare, each a bool or an integer with a range ("nothing a rule reads is a float")**, so a material's density is an integer in a declared range and C7's "integers" is already built in **[read: `engine/block_models/src/property.rs`]**; `engine:density` exists today. `BlockTable` makes one column for each key, indexed by block and state, so a million blocks with ten properties is tens of megabytes **[believed: I did not check the width of an entry]**, one more reason a client's table holds only the materials it has met. Physics, meshing, shapes, states and whatever the item system does with blocks work as they do. The alternative, one generic block and a "material number" channel, never grows the registry and avoids the ordering leak, but every reader of a block would read two channels and items would have to name a pair; **I would not.** Medium.
- **The "generated pack" is right as a form** (a canonical archive with an index and a root hash, cached by hash, checkable) **but not in the global pack list**: `Packs` replaces a client's whole list and `PackageReplaced` resends the package **[read]**, which suits a few authored packs and not an unbounded stream. **A material set for each planet, in the same archive form, sent to a client when it first needs one** (it reaches the planet, or holds an item), held while needed, and **evicted by the client when pictures run out** (`set_picture` writes one place of the 1,024 at run time **[read]**, so a cache is possible; it is not built). Medium.
- **Pictures are rendered by the server and sent as pixels, as the engine sends them today.** The alternative, sending the recipe and a leaf seed and rendering on the client, saves bandwidth (a recipe is tens of bytes, three pictures of 16 x 16 are about 3 KiB) and makes every recording depend on the synthesis code for ever; pixels are the truth. Start with pixels. Medium.
- **Where it meets the wasm host plan** (`wasm-generator-host-spec.md`): a module writes *palette slots*, and the host maps slots to the world's block ids. For a planet, the slot-to-material table is that planet's material set, so **a planet's generator can only be built when its material set has arrived**: the same "generator built late, ground not drawn until then" the host plan's client step already needs. The first user of the host and the first user of materials are the same thing, a planet. **[believed]**

## 7. What the engine would need, in the order I would build it

Sizes are **[believed]** and relative; each step ends with tests, clippy, fmt, doc and a push.

1. **The rules and the canary test first**: C1 to C8 written as standing rules (once you agree), and the canary scan with a stand-in key type, before there is a secret to leak. *Small.*
2. **`secret_derivation`** (an engine crate): the `SecretKey` type, derivation by named purposes, known-answer tests against the published vectors of the primitive, tests that purposes and widths separate, a mutation run. **Uses `blake3`, chosen by the owner** (section 8, question 2) and already in the tree for pack hashes. *Small.*
3. **The withheld section**, `describe` leaving it out, a replicated world having none, the root drawn at creation. **A world-format change (yours).** *Small to medium.*
4. **The material generator** (a plugin, on the game's side of the line): properties from PRF bytes and the planet-kind dial, pictures from authored textures and noise, definitions saved, opaque ids; headless statistics over a thousand planets (distributions, no id collision, no id that contains a planet's number). *Medium; which properties and ranges is yours.*
5. **Delivery on demand**: the new messages (a material set, an eviction), the client's block table growing at run time, the picture cache. **The wire is yours.** *Large, and the one with the risk.*
6. **Per-client numbering** (C4 b) only if you ask.

## 8. Questions for the owner

1. **The rules** (C1 to C3, C6 to C8): secrets of at least 128 bits from the OS; derivation only through a keyed cryptographic hash, the engine's `mix` and noise for public seeds only; terrain seeds public and a separate branch from the materials; a withheld section with a type that cannot be sent and a canary test; definitions saved when made; no secret in gameplay randomness. As standing rules? My pick: **yes**.
2. **The primitive**: **answered, BLAKE3** (owner, 2026-11-26). The question was HKDF-SHA256 (builds on the `sha2` already in the tree; RFC 5869 has test vectors) or BLAKE3 (one crate with a keyed mode and a key derivation mode, faster, new); my pick had been HKDF-SHA256, with low-medium confidence, and either is sound. The `blake3` crate comes in with `secret_derivation` (section 7, step 2). The owner then said pack archives move too: their hashes are BLAKE3 since 2026-11-26 (`pack-archive-spec.md`), so the crate is already in the tree.
3. **M1**: a client learns a material only when it sees or holds it, from the start? My pick: **yes**.
4. **A material is a block** (a registry entry), not a channel value? My pick: **a block**.
5. **M2**: how much may a planet's public kind decide a material's properties? Your call; my pick: a coarse public kind moves ranges, never identity.
6. **A replicated world carries no root** (undiscovered planets cannot be explored in a copy)? My pick: **yes**.
7. **C4**: accept consecutive numbers as a known leak in version 1? My pick: **yes**.
8. **Order of work**: the wasm host (its steps 1 to 3 change no format) first, or this? They meet at a planet whose material set must arrive before its generator is built. My pick: **the host's steps 1 to 3 first**, then the rules, the canary test and `secret_derivation`, which need no decision about the host.

## 9. The next round: seeds to the client, far colour, traits, wasm generators (2026-11-27)

**The owner's ideas** (not final): the client may be sent a material's seed after all, but not as early as its levels of detail are drawn, or passing or orbiting a planet would give every property of its surface; far off, the client should know a material's **colour** without its seed, and the owner wants opinions on how. A terrain generator might **declare traits** of a material ("sedimentary", "purple", an exact colour), known to the client before the pack exists; the material then comes from a seed with overrides, or the seed is kept from influencing those traits, or the server searches for a seed that fits. **Several material generators** in one world, third-party ones as **wasm** that the client downloads to make packs from seeds, so that the server's folder of packs is only a **cache**. The server keeps for ever which materials have been made, where they came from (a later technology may give hints), who found them and the name the finder gave; **the first player to pick one up names it**. This changes section 6: pictures would be made by the client, not sent.

**What is already so [read].** A coarse cell holds a dominant block id, a fill fraction and a light level, and is **never textured** (`lod-spec.md`, decisions 6 and 7), so far terrain needs one flat colour for each material, and its glow if it has one. A block with a texture may take its colour from the average of its pictures (`color_from_pictures`); a material cannot, since the colour comes before the pictures.

**My opinions** (**[believed]** throughout; nothing is built or measured):

- **9a. Sending the seed is safe for origin**, if it is a leaf: `keyed_hash(planet's material key, ...)` leads back to nothing. What it gives away is everything the generator makes from it, so a property meant to be found by experiment cannot be hidden from a changed client that holds the seed. High.
- **9b. Two seeds, not one**: a **look seed** (textures, roughness, metallicity, glow) and a **property seed** (density, hardness, friction and the rest), neither derivable from the other. The look seed goes when a player is near enough to see detail, by a radius the **server** sets (the texture distance is the client's own setting and must not decide); the property seed when the material is picked up or assayed. A link between look and properties is then possible only through a declared trait. High on the split; the triggers are the owner's.
- **9c. Far colour**: the server sends, for each material of a planet it shows, an **opaque id and a far colour** (and glow), computed by a small export of the generator that makes no textures; the client's table entry is upgraded when the seeds come. **Round the colour coarsely** (a few hundred colours in all): an exact colour is a fingerprint that lets a player who has only orbited many planets match a bought block to one; with 256 colours a block matches about one material in 256. The price is a visible change of colour on approach. Medium; how coarse is a matter for pictures.
- **9d. Traits**: make them **inputs of the generator**, `generate(seed, traits)`, which draws within what they allow (the owner's first two options are this one). **Do not search for seeds**: an exact colour is one value in 16.7 million, the cost depends on a third party's code, and it breaks when the code changes. Traits are namespaced keys with integer values, a generator says which it takes, and an unknown one is an error at load. A trait is **public** (it comes from a terrain generator run on public seeds): it must never depend on a secret, and each one is a clue to origin. A declared colour needs no message from the server, and anyone can work it out for a planet never visited. High on no search.
- **9e. The pack folder is a cache only if everything that makes a pack is kept**: for each material the generator module (by BLAKE3 hash), the root hash of the authored textures, the interface version, the traits and both seeds. A world keeps those modules and textures as long as it has a material made by them; a new version of a generator makes new materials only and never changes old ones. High.
- **9f. Save the properties too** (about a hundred bytes a material), as C7 says: pictures are cache, but an item someone paid for must not change or lose its numbers because a module is missing or wrong, and physics should not wait on one. Save the seeds as well, so that a copy of a world needs no root (C6). Medium-high.
- **9g. A third-party generator gets leaf seeds and traits and nothing else**, never a planet's key; no imports, fuel and memory limits on client and server, and its output checked against the declared ranges. Which generator made a material is itself a clue to origin if planets differ in generator. High.
- **9h. Origin is the secret in the record**: it stays in the withheld section, never in a replicated world or a recording. A hint technology sends a deliberately coarse answer that is **the same every time it is asked** for one material, so that repeating cannot average it away. High.
- **9i. Names**: the first pick-up in the server's order wins; a name is checked like a nickname, has a default if the finder gives none, and an operator can change it. Showing the finder's name publicly tells buyers whom to follow; let the finder choose. Medium.

**New questions for the owner:** (a) two seeds (9b)? my pick yes; (b) far colour from the server, coarsely rounded (9c), or colours declared by terrain generators and so public? my pick the first, with a declared trait overriding it; (c) properties saved for ever beside the seeds (9f)? my pick yes.
